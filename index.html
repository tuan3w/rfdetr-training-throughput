The problem

The production job trains RF-DETR Medium on 164,334 person/face images on one shared A100 at 1.30 it/s with batch 8 = 10.4 img/s, i.e. 4h23m per epoch and ~18 days for the configured 100 epochs. The script carried a stack of workarounds added after repeated Xid 31 MMU faults: math-only SDPA, a SciPy-forced Hungarian matcher, non-fused AdamW, gradient checkpointing and the classic CUDA allocator.

During this work the job crashed again — Xid 31 at 12:30:22 — while running the full workaround stack. The workarounds cost 1.6-2x throughput and did not prevent the fault, and the Xid history spans both tenants of the shared GPU, so the cause is more likely the torch 2.14+cu130 / driver 595 stack or the co-tenancy than any of the three flags.

How it was measured

Everything was measured on the local RTX 5060 Ti, exclusively and reproducibly, against a fixed 3,000-image subset of the production dataset, using the real PyTorch Lightning training loop (dataloader → augmentation → AMP forward → matcher/criterion → backward → optimizer → EMA). The shared A100 was used only as a target-hardware cross-check, because a neighbour's Jupyter kernel holds 22.5 GiB and pins it at 100% utilisation.

The harness reproduces production faithfully: the A100 cell running the live config measured 10.04 img/s against the real job's observed 10.4 img/s. Each reported number is the median of independent processes (2-3 repeats of 40 measured steps after warm-up), and lab/guard.py fails any run that buys speed by weakening training — resolution, multi-scale set, effective batch, augmentation stack and EMA are all pinned.

The custom kernels

Matcher cost matrix (kept, +20%). The profiler found aten::_cdist_forward at 15.3% of all device time in 5 calls per step. rf-detr builds the Hungarian cost matrix as a chain of separate kernels — class gather, focal cost, cdist L1, two box conversions, a vmapped GIoU, then three multiplies and two adds — each pass reading and writing a full [B, 3900, T] tensor. One fused Triton kernel replaces all of it and is 174x faster standalone on the production shape (25.4 ms → 0.145 ms). rf-detr ships no custom kernels at all, so this path was unoptimised ground.

Exact GPU assignment solver (kept, +20.9%). A CUDA port of SciPy's rectangular_lsap, one block per problem, returning zero index differences against SciPy on every matcher shape. Porting SciPy rather than writing a textbook Hungarian mattered: its inner loop removes exactly one column per iteration, which bounds the augmenting search — the first attempt, built from the usual formulation, had no such bound and hung the GPU. Cost is roughly quadratic in target count (0.12 ms at 12 targets, 1.40 ms at 108, 76.8 ms at 300), but so is the host path it replaces, and the kernel wins at every size measured: 1.6 vs 48 ms at 128 targets, 7.0 vs 92 at 219, 76.8 vs 217 at 300.

Deformable attention (three attempts with the real CUDA kernel, none kept). rf-detr runs deformable attention through the reference PyTorch decomposition, whose own docstring says "For debug and test only, need to use cuda version instead", and no compiled extension is installed (import MultiScaleDeformableAttention fails). Its fp32 grid_sampler_2d_backward is the largest non-GEMM kernel in the profile. A fused Triton kernel was +2.9% eager but -4.0% under compile; the real Deformable-DETR CUDA kernel — fetched prebuilt from the Hugging Face kernels hub for this exact torch/CUDA build — is far faster on the operator yet does not move the step time:

Paired Nsight traces say why, and it is not the kernel: per 1.2 s window it replaces 59.7 ms of grid_sampler with 41.7 ms of im2col/col2im, but aten layer-norm kernels around the attention block go from 24 to 48-54 calls (+16.9 ms) and cast kernels add 12.8 ms — the opaque call splits an Inductor-fused region, and the fp32 conversions its contract requires are no longer fused either. Registering it as a custom op, the textbook fix for a graph break, was worse again. The conclusion is about this model rather than the kernel: while the decoder region is compiled, any opaque deformable-attention implementation loses more to lost fusion than a 2.7-3.5x operator speedup returns. It becomes worth keeping if the model is ever compiled end to end, or in an eager configuration (+2.4%).

The two surprises

The solver did belong on the GPU after all. NVTX attribution showed the host spending 102 ms per microbatch inside the criterion — as much as the entire backward pass — because the SciPy assignment solve drains the GPU pipeline five times per step. Moving it to the GPU with the solver rf-detr already supports lost 35%, which looked like proof that ~520 tiny problems ([300 x T], T between 1 and 219) are inherently latency-bound and belong on the host; an 8-thread pool gained 13.3% and that was the accepted answer. It was the wrong conclusion: that solver is built for large square problems. A solver written for this shape gained a further 20.9%, and criterion host time fell 102 → 72 → 42.8 ms across the three generations.

The inter-batch gap was not overhead. ~42 ms per microbatch sits between one batch ending and the next starting, and it is not the loader: replaying cached batches with zero workers leaves it unchanged. Timing every blocking primitive showed a single lightning_utilities apply_func.py:134 to_item() call per microbatch holding 35.65 ms — Lightning converting the logged loss dict to Python floats, waiting for the GPU to drain. It is mostly overlapped device work, so there is no 42 ms of host overhead to reclaim; device idle attributable to that window is ~3.5 ms.

An upstream bug worth reporting

Structured Dynamo logs (tlparse) show that with compile=True the model forward never compiles at all: seven compile ids, all rooted at lwdetr.py:477, fail with Expected IntList but got GenericList from _upsample_bicubic2d_aa_backward. The DINOv2 positional-embedding resize gets a symbolic output size because rf-detr compiles with dynamic=True, and the antialiased-bicubic backward cannot accept one; suppress_errors=True then hides the failure and the dominant compute runs eager.

Whether that is a loss took two measurements to settle, because the first one was wrong. An earlier version of this report claimed the compiled encoder was 0.60x; that was a benchmark bug, not a result. The loss was taken from features[0], but this encoder returns one feature map per out_feature_indexes layer, so the gradient only reached the layers feeding the earliest map: eager ran 3 attention backwards against 12 forwards (0.55x the forward's GEMM calls) while the compiled graph computed all 12 (2.14x). The two sides were doing different amounts of work, and the forward alone being faster compiled (14.48 vs 16.22 ms of GEMM time) was the clue.

With the loss summed over every returned map, the answer depends entirely on the compile mode:

End to end that holds: with the missing meta supplied so the backbone actually compiles, 37.50 img/s against 44.08 for the eager control (-14.9%, 16 workers, warm cache, 60 warm-up steps). Paired Nsight traces put it on Inductor's codegen rather than the backbone's math — triton kernel time 125.9 → 222.6 ms per 1.2 s window (+596 calls) and GEMM +24.7 ms, against elementwise -14.6 ms.

Supplying the meta kernel torch is missing settles it end to end. The graph is then accepted -- seven failing compile ids become zero, and the compiled dynamic backward matches eager bit-exactly on the output and to 6e-07 on the gradient -- and against a matched control the compiled backbone is 32.27 vs 35.51 img/s, -9.1%, agreeing with the 0.60x encoder figure. (Both rows use 4 dataloader workers rather than the kept 16, because the symbolic-shape compile otherwise does not fit in RAM and systemd-oomd kills the run.)

On the 108-SM A100 — where autotuning is available and compile did help in the cross-check (14.82 → 15.99 img/s) — a compiled backbone may well win, and nobody can find out while the resize rejects the graph. That is the argument for reporting it upstream, filed as pytorch/pytorch#197622. The three repairs tried here all cost more than they return: disabling Dynamo for just the resize makes Inductor attempt the real graph (22 minutes on one frame, GPU idle, one core pinned on sympy shape reasoning over an ~800 KB FX graph); dynamic=False compiles at 2-3 min per resolution across 8 multi-scale sizes; per-block compilation measured 43.17 against 45.24 img/s.

Recommended production configuration

--sdpa-backend auto --fused-optimizer --no-gradient-checkpointing --batch-size 16 --grad-accum-steps 2, compile=True on the model constructor, plus the three accepted patches (triton_matcher, cuda_lap, device_indices). Reduce epochs from 100 to 25-30 (the rf-detr docs recommend 20-30 above 10k images; this dataset has 164k), and eval_interval 5, eval_batch_size 16, eval_max_dets 100. Keep what was already right: pack_targets, 16 workers, thread pinning and expandable_segments:False.

Where the remaining time goes

The device is now 85.4% busy, up from 69.9% when this started, so the step is genuinely GPU-bound and further host-side work has little left to win. Of the 14.6% idle, 48% is 10,612 gaps of 5-50 us — launch latency from an eager model graph — and 25% is 20 gaps over 1 ms at the microbatch boundaries. Removing the launch latency needs either CUDA graphs (ruled out: one memory pool per multi-scale shape, 12.3 GiB after 2 of 8 shapes) or a compiled model graph, which is exactly what the upstream dynamic=True bicubic bug prevents. Device time itself is dominated by real work: bf16 cutlass GEMMs hold the top three entries at 138/125/75 ms per 1.4 s window.
